## Тухай

Энэ лабораторийн ажил нь Maven-д суурилсан Java төсөл дээр JUnit 5 (Jupiter) хүрээгээр `GradeCalculator` классын нэгжийн тестүүдийг бичсэн ажил юм. `GradeCalculator` нь оюутны нийлбэр онооноос үсгэн дүн тооцох (`letterGrade`) болон ирц, лаб+бие даалт, сорил1, сорил2, шалгалтын онооноос нийлбэр оноо тооцох (`totalScore`) функцтэй. Тестүүд нь Arrange-Act-Assert бүтэцтэй, хязгаарын утгуудыг (boundary values) шалгасан, `assertThrows` ашигласан, мөн 2 parameterized тест агуулсан. Эцэст нь `letterGrade`-ийн `score >= 90` нөхцөлийг зориуд `score > 90` болгож мутаци хийж, тестүүд үнэхээр алдаа илрүүлж чадаж байгааг баталгаажуулсан.

## Ажиллуулах заавар

```bash
mvn test 2>&1 | tee results/mvn-test.txt
```

## Тестийн тоо

`results/mvn-test.txt`-ийн сүүлийн мөр:
```
Tests run: 25, Failures: 0, Errors: 0, Skipped: 0
```

**25 тест ажилласан.** Энэ нь 14 бие даасан `@Test` метод + 2 `@ParameterizedTest` метод (нэг нь `letterGrade`-д зориулсан 8 мөр `@CsvSource`, нөгөө нь `totalScore`-д зориулсан 3 мөр) = 14 + 8 + 3 = 25 гэсэн үг. Өөрөөр хэлбэл, метод тоо (16) ба Surefire-ийн тоолсон "Tests run" тоо (25) хоорондоо ялгаатай — яг лабораторийн зааварт анхааруулсанчлан.

`BUILD SUCCESS` — бүх тест ногоон.

## Тестийн бүтэц

- **letterGrade ердийн утгууд**: 95→A, 65→D, 30→F
- **letterGrade хязгаарын утгууд**: 90 (A), 89.99 (B), 60 (D), 59.99 (F), 0 (F), 100 (A) — эдгээр бүгд тусдаа `@Test`-ээр давхар шалгасан, мөн `@ParameterizedTest`-ийн `@CsvSource`-д давтагдсан
- **letterGrade буруу оролт**: -1 болон 101 → `assertThrows(IllegalArgumentException.class, ...)`
- **totalScore хэвийн утга**: бүх дээд хязгаараар (10, 40, 10, 10, 30) → 100
- **totalScore буруу оролт**: att = -5 (сөрөг) болон lab = 41 (дээд хязгаараас хэтэрсэн) → `assertThrows`
- **Parameterized тестүүд**: `letterGradeBoundaries` (8 мөр), `totalScoreValidCombinations` (3 мөр)

## Мутаци (мутациjн тест)

`GradeCalculator.letterGrade`-ийн дараах мөрийг:
```java
if (score >= 90) return "A";
```
зориуд дараах болгож өөрчилсөн:
```java
if (score > 90) return "A";
```

Дараа нь `mvn test 2>&1 | tee results/mvn-test-mutant.txt` ажиллуулсан. Үр дүн:

```
Tests run: 25, Failures: 2, Errors: 0, Skipped: 0
Failures:
  GradeCalculatorTest.letterGradeBoundaries:106 expected: <A> but was: <B>
  GradeCalculatorTest.ninetyIsExactlyA:48 expected: <A> but was: <B>
BUILD FAILURE
```

Хоёр тест мутацийг илрүүлсэн: `ninetyIsExactlyA` (тусдаа бичсэн хязгаарын тест) болон `letterGradeBoundaries`-ийн `90,A` мөр (parameterized тестийн нэг тохиолдол). Хоёулаа score=90 үед "A" хүлээгдэж байсан ч мутацийн дараа "B" буцаж эхэлсэн тул унасан. Нэгээс олон тест нэг мутацийг барьж авсан нь хязгаарын нөхцөлийг зөвхөн нэг аргаар биш, давхар аргаар (тусдаа `@Test` ба `@ParameterizedTest` мөрөөр) шалгасан байгааг нотолж байна.

Дараа нь `score >= 90`-ийг буцааж сэргээж, `mvn test`-ийг дахин ажиллуулсан — `results/mvn-test.txt` дахин `Tests run: 25, Failures: 0`, `BUILD SUCCESS` гарсан (ногоон хэвээр).

## Дүгнэлт

Энэ лабораторийн хамгийн сонирхолтой хэсэг бол мутацийн тест байсан — учир нь энэ нь "тест бичсэн" гэдэг нь "тест зөв ажилладаг" гэсэн үг биш гэдгийг практикт харуулсан. Хэрэв би зөвхөн ердийн утгуудыг (95, 65, 30) шалгасан бол `>=90`-ийг `>90` болгосон ч миний тестүүд бүгд ногоон хэвээр байх байсан — учир нь тэдгээр ердийн утгууд хязгаарт хүрдэггүй. Яг 90 гэсэн хязгаарын утгыг тусгайлан шалгасан хоёр тест (нэг `@Test`, нэг parameterized мөр) л энэ мутацийг барьж чадсан. Энэ нь Лекц 2-т үзсэн "алдаа ихэвчлэн хязгаар дээр нуугддаг" зарчмыг бодит кодоор баталгаажуулсан жишээ боллоо. Хамгийн хэцүү санагдсан зүйл бол `totalScore`-ын 5 параметрийн хослолыг бүрэн хамарсан тест бичих байсан — учир нь параметр тус бүрийн хувьд "сөрөг" ба "дээд хязгаараас хэтэрсэн" гэсэн 2 тохиолдол байдаг тул онолын хувьд маш олон комбинац гарна; би хамгийн чухал 2 тохиолдлыг (att сөрөг, lab хэтэрсэн) сонгож бичсэн бол бусад параметрт мөн адил логик хэрэгжсэн гэдэгт итгэсэн. Дараагийн удаа PIT зэрэг автомат mutation testing хэрэгслээр илүү системтэйгээр шалгаж үзэхийг хүсэж байна.
